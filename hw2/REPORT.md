# ИДЗ-2: асинхронная модель сортировочной станции

Подлягин Данил Денисович, БПИ253. Вариант 49.

## Что моделирует программа

На станцию поступают составы с вагонами разных направлений. После расцепки
вагоны ожидают назначения локомотива. Диспетчер выбирает сортировочный путь
и маршрут, локомотив выполняет сцепку и манёвр. Когда на пути собран требуемый
комплект, формируется и отправляется новый поезд.

Вместимость сортировочных путей ограничена. Конфликтующие маршруты нельзя
занимать одновременно, а один локомотив выполняет только одно задание.
Каждый вагон имеет единственное местоположение и не может отправиться дважды.

В отличие от ИДЗ-1, участники работают в отдельных потоках. Независимые
манёвры перекрываются по реальному времени, а не воспроизводятся общим
последовательным циклом. Реализация написана на C17 для Linux с pthread.

## Сборка и запуск

Из папки `hw2`:

```bash
make
./station examples/parallel.scenario 100
./station-cond examples/parallel.scenario 100
make test
```

Нужны компилятор C, make, pthread, libm и стандартные утилиты Linux.
Сборка включает `-Wall -Wextra -Wpedantic -Werror`.

| Параметр | Значение |
| --- | --- |
| `--scenario PATH` | файл данных; по умолчанию examples/station.scenario |
| `--tick-ms N` | миллисекунд в единице модели; 1..1000, по умолчанию 100 |
| `--until N` | предел модельного времени; 0 - без предела |
| `--strategy first\|most` | приоритет комплектов по порядку путей либо их вместимости |
| `--log PATH` | журнал; по умолчанию station.log |
| `--quiet` | отключение табло |
| `--help` | справка |

Сценарий и масштаб также принимаются двумя позиционными аргументами.
`make clean` удаляет результаты сборки и журналы в текущем каталоге.

## Входные данные

Формат сохранён из ИДЗ-1:

```text
track=id,purpose,capacity
locomotive=id,speed
route=id,from_track,to_track,length,conflict|conflict
wagon=id,arrival_id,destination
arrival=id,time,track
requirement=id,destination,wagon_count,track
timing=uncoupling,coupling,maneuver
strategy=first_fit
```

Вместо конфликтов допустим `-`; перечисленные конфликты должны быть
симметричными. Вторая стратегия в файле - `most_free_capacity`.
Пустые строки и комментарии с `#` пропускаются.

Загрузчик проверяет обязательные поля, ссылки, уникальность идентификаторов,
назначения путей и достижимость. Числа разбираются через strtol/strtod с
проверкой errno, конца строки и диапазона. Пустые поля, NaN, бесконечность и
переполнение отвергаются.

Целые значения ограничены 1 000 000; идентификаторы и время прибытия могут
быть нулевыми, вместимости и длительности положительны. Скорости и длины
лежат в диапазоне 0.000001..1000000. Для каждой пары маршрута и локомотива
время движения не превышает 1 000 000 единиц. Имена содержат до 31 символа
из букв, цифр, дефиса и подчёркивания; строка - до 254 символов.
Число сущностей ограничено массивами в station.h.

## Участники и общие ресурсы

| Участник | Работа отдельного потока |
| --- | --- |
| прибывающий состав | ожидает прибытия и расцепки, уведомляет свои вагоны |
| вагон | после расцепки публикует заявку, ожидает включения в новый поезд |
| диспетчер | назначает доступные совместимые задания |
| локомотив | получает задание, выполняет сцепку и движение |
| отправляемый поезд | проверяет и забирает свой полный комплект |

Основной поток запускает участников, принимает сигналы, контролирует срок
и обновляет табло. Пути и маршруты - пассивные ресурсы под общим мьютексом,
поскольку собственного активного поведения у них нет.
Для parallel.scenario создаётся восемь рабочих потоков и один основной.

Вагон проходит состояния PLANNED $\rightarrow$ WAITING $\rightarrow$ MOVING $\rightarrow$ SORTED $\rightarrow$ DEPARTED.
Поле departure_id сохраняет связь с отправленным поездом.

## Планирование и синхронизация

До запуска потоков планировщик выбирает полные комплекты. Каждому месту
поезда сопоставляется вагон, достижимый до нужного пути. Используется поиск
увеличивающих путей в двудольном графе: ранее выбранный гибкий вагон можно
переназначить, освобождая место для вагона с единственным маршрутом.
Если новый комплект нельзя наполнить целиком, его изменения откатываются.

Такой предварительный план устраняет случай, когда простой first-fit разносит
два вагона по разным путям и теряет возможность собрать поезд из двух вагонов.
Переназначение выполняется только до движения. Комплекты на одном пути
обслуживаются последовательно; вагоны без плана сортируются после плановых.
`first` рассматривает комплекты по порядку путей, `most` - по убыванию
вместимости. Глобальная максимизация числа отправленных вагонов не выполняется.

Все изменения модели защищены одним мьютексом. Диспетчер одновременно
резервирует локомотив, маршрут и входящее место на пути: поток не удерживает
часть ресурсов в ожидании остальных. Задержки, ожидание уведомлений, join
и вывод табло выполняются без удержания мьютекса станции.

Из одного набора исходников собираются две программы:

- station - личные POSIX-семафоры участников;
- station-cond - условные переменные с внутренним мьютексом и счётчиком.

Счётчик сохраняет раннее уведомление. Ожидание условной переменной выполняется
в цикле, учитывая ложные пробуждения. После уведомления участник повторно
проверяет состояние модели. Внутренний мьютекс уведомления освобождается
до захвата мьютекса станции; обратного порядка удержания блокировок нет.

Перед стартом основной поток ожидает готовность всех участников. При частичной
ошибке запуска уже созданные потоки получают остановку и присоединяются.
Синхропримитивы уничтожаются только после join. pthread_cancel не используется.

## Время, интерфейс и завершение

Отсчёт CLOCK_MONOTONIC начинается после готовности участников. Длительность
движения - максимум заданного времени манёвра и ceil(length/speed).
Порядок независимых событий зависит от планировщика ОС и может различаться.

Главный поток обновляет 80-символьное табло каждые 100 мс из снимка данных.
На нём видны вагоны, локомотивы, заполнение путей и последние восемь событий.
При перенаправлении вывода управляющие последовательности не печатаются.

Полная история записывается через файловый дескриптор. События ARRIVE,
UNCOUPLE, ASSIGN, RESERVE, START, FINISH, PLACE, FORM и DEPART отражают этапы
задания. seq задаёт порядок записей, time_ms - время от старта. Запись под
мьютексом сохраняет порядок строк, но медленный журнал может задержать модель.

SIGINT и SIGTERM блокируются перед созданием участников и принимаются главным
потоком через sigtimedwait. После остановки пробуждаются ожидающие участники;
задержки проверяют флаг каждые 10 мс. Сохраняется согласованный частичный
результат: незаконченные манёвры не объявляются завершёнными.

| Код | Причина |
| ---: | --- |
| 0 | отправлены все вагоны и обработаны все объявленные прибытия |
| 1 | ошибка входных данных, ОС или записи журнала |
| 2 | достигнут предел времени |
| 3 | нарушен инвариант |
| 4 | продолжение невозможно, остались неотправленные вагоны |
| 5 | SIGINT или SIGTERM |

Остаток диагностируется только при отсутствии будущих прибытий, активных
манёвров и готовых комплектов. Последнее условие не позволяет завершиться
раньше, чем проснётся поток готового к отправлению поезда.
В конце журнал содержит SUMMARY и конечную/пиковую занятость TRACK.

## Проверка корректности

state.c проверяет единственность владельца вагона, обратную связь локомотива
и задания, соответствие маршрута источнику и назначению, конфликты резервов,
вместимость с учётом входящих вагонов и точный состав отправленных поездов.
Проверки выполняются перед и после назначения, после размещения и отправления,
а также после join. Нарушение останавливает модель с событием INVARIANT.

`make test` - единая команда для обеих реализаций. Она запускает по 46
модульных проверок, сценарные проверки, сопоставление исходов двух программ
и имитацию ошибок запуска. Независимый анализ журнала проверяет нумерацию,
монотонность времени и цепочки событий каждого вагона.
Для планировщика проверены все 256 графов достижимости четырёх вагонов
и двух поездов по два вагона с сопоставлением с полным перебором.

| Набор или действие | Проверяемый результат |
| --- | --- |
| station | отправлено 2 вагона; join 7 участников |
| parallel / conflicting | максимум 2 / 1 одновременно назначенных манёвра |
| capacity / remainder | нет переполнения; корректный код остатка 4 |
| strategy | разные приоритеты first и most |
| allocation / flexible | полный комплект и ограниченная достижимость |
| groups | последовательные комплекты на тесном общем пути |
| large | 48 вагонов, четыре отправленных поезда, join 61 участника |
| empty-arrival | ожидание объявленного прибытия даже без вагонов |
| SIGINT / SIGTERM / --until | пробуждение, join и частичный результат |
| неверные данные | отказ загрузки с кодом 1 |

Тестовые программы station-fail и station-cond-fail подменяют функции запуска
через механизм линкера --wrap. Проверяются отказы создания первого, третьего
и восьмого потоков, инициализации уведомлений и запись в /dev/full.
В обычных бинарниках этих тестовых переключателей нет.
Две реализации сравниваются на двенадцати сценариях по результату и составам
поездов, без требования одинакового порядка независимых событий.

Результаты можно воспроизвести командой `make test`.

## Ограничения модели

Вместимость контролируется для сортировочных путей; путь прибытия служит
источником маршрутов. Не моделируются геометрия стрелок, масса вагонов и
положение локомотива между заданиями. Стратегии приоритетные, не оптимальные.
Строгая справедливость планировщика ОС не гарантируется. Число участников
конечно, память ограничена статическими массивами.

## Расположение кода

+ main.c - вход и сигнальная маска
+ config.c - параметры
+ scenario.c - сценарии
+ plan.c - комплекты
+ engine.c - потоки и табло
+ state.c - инварианты
+ notify.c/notify.h - уведомления
+ station.h - типы
+ tests.c и tests_fail.c содержат модульные проверки и подмены для отказов


В scripts/ оставлены один сценарный тестовый скрипт и анализатор журнала.
В examples/ находятся четыре демонстрационных сценария: station, parallel,
conflicting и remainder. Восемь специальных регрессионных наборов вынесены
в test-data/. Ошибочные входы проверяются в tests.c без отдельных файлов.
